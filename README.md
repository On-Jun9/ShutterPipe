# ShutterPipe

사진/영상 파일을 촬영일시 기준으로 자동 백업 및 분류하는 도구

## 주요 기능

- **메타데이터 기반 분류**: EXIF/XML 데이터를 읽어 촬영 날짜별로 자동 분류
- **날짜 필터링**: 특정 기간의 파일만 선택적으로 백업 (오늘/최근 7일/최근 30일/전체)
- **웹 UI**: 브라우저에서 설정 및 실시간 진행 상황 확인
- **프리셋 관리**: 자주 사용하는 설정을 저장하고 불러오기
- **설정 영속성**: 서버 측 JSON 저장으로 다중 브라우저 간 설정 공유
- **백업 취소**: 진행 중인 백업에 취소를 요청하고 현재 파일 I/O가 반환되는 시점에 중단 결과를 이력에 기록
- **백업 검증**: 원본과 백업본을 새로 스캔해 실제 파일끼리 대조하고(기존 기록 미의존), 누락·불일치 파일은 다음 백업 때 다시 복사되도록 예약
- **백업 이력 관리**: 최근 백업·검증 결과를 이력 탭에서 조회 및 필터링
- **중복 검사**: 파일명+크기 또는 해시 기반 중복 파일 감지
- **충돌 처리**: Skip/Rename/Overwrite/Quarantine 정책 선택
- **경로 북마크**: 자주 사용하는 경로를 저장하여 빠른 접근

## 사용법

### 1. 서버 실행

```bash
./start.sh
```

서버가 백그라운드에서 실행되며 `http://localhost:8080`에 접속할 수 있습니다.

#### 포트 변경

```bash
./bin/shutterpipe-web -addr "localhost:9090"
```

`start.sh`는 기본값인 `localhost:8080`으로 실행합니다. ShutterPipe 웹 UI는 로컬 전용이며,
보안을 위해 `localhost` 또는 loopback IP(`127.0.0.1`, `::1`)에만 바인딩할 수 있습니다.

### 2. 웹 UI 접속

브라우저에서 `http://localhost:8080` 접속

### 3. 경로 설정

- **원본 경로**: SD 카드 또는 소스 디렉토리 경로 입력
- **목적지**: 백업할 NAS 또는 로컬 디렉토리 경로 입력

원본과 목적지는 서로 같거나 어느 한쪽이 다른 쪽 내부에 있을 수 없습니다. 심볼릭 링크를 해석했을 때 경로 트리가 겹치는 경우도 실행 전에 거부하여 자기 자신으로의 복사와 이전 백업 결과의 재스캔을 방지합니다.

원본 폴더 안의 심볼릭 링크와 특수 파일(FIFO 등)은 백업·검증 대상에서 제외됩니다.

목적지 내부의 기존 심볼릭 링크가 설정된 목적지 밖을 가리키면 하위 디렉토리를 만들기 전에 해당 작업을 실패 처리합니다. 이 검사는 정상적인 로컬 전용 운용을 위한 경계이며, 동일한 파일 권한을 가진 다른 프로세스나 NAS 사용자가 검사와 파일 생성 사이에 디렉토리 구조를 적대적으로 교체하는 상황까지 방어하지는 않습니다.

### 4. 분류 방식 선택

#### 날짜별 분류 (기본)
```
목적지/
├── 2025/
│   ├── 01/
│   │   ├── 01/
│   │   │   ├── IMG_1234.jpg
│   │   │   └── VID_5678.mp4
│   │   └── 02/
│   └── 02/
```

#### 이벤트별 분류
```
목적지/
├── 2025/
│   ├── 250101-크리스마스/
│   │   ├── JPG/
│   │   │   └── IMG_1234.jpg
│   │   ├── MP4/
│   │   │   └── VID_5678.mp4
│   │   └── RAW/
│   │       └── IMG_9999.cr2
```

- 이벤트명이 비어 있으면 `250101`처럼 날짜만 사용합니다.
- 파일 타입 폴더는 `JPG`, `MP4`, `RAW`로 분류됩니다.

### 5. 백업 시작 및 취소

설정 완료 후 "백업 시작" 버튼 클릭

백업이 시작되면 진행 상황이 실시간으로 표시됩니다. **취소** 버튼을 클릭하면 취소 신호가 각 처리 단계에 전달되고, 진행 중인 파일 I/O 호출이 반환되는 시점에 중단됩니다. 취소된 백업은 취소 시점까지 처리된 파일 통계와 함께 이력에 기록됩니다.

취소 요청에는 시작 응답에서 받은 실행 ID(`run_id`)와 서버 프로세스 ID(`server_id`)가 반드시 포함되어야 하며, 둘 다 현재 서버와 실행에 정확히 일치할 때만 처리됩니다. 같은 서버 프로세스에서는 완료된 `run_id`를 재사용하지 않습니다. 이는 이전 실행이나 재시작 전 서버의 지연된 취소 요청이 새 실행에 영향을 주는 것을 방지합니다.

`overwrite` 정책에서 한 실행의 여러 원본이 같은 목적지 이름을 만들면 스캔 순서상 마지막 원본을 결정적인 최종본으로 사용합니다. 같은 그룹의 앞선 원본은 최종 파일로 남지 않으므로 모두 보존해야 하는 백업에는 `rename` 정책을 사용하세요.

`skip`, `rename`, `quarantine`은 계획 이후 생긴 파일도 덮어쓰지 않고 symlink 경합으로 목적지 루트 밖에 쓰지 않도록, 열린 목적지 루트를 기준으로 hard link publish를 수행합니다. hard link를 지원하지 않는 파일시스템(exFAT/FAT, 일부 SMB 공유)에서는 "존재 확인 후 이름 변경" 폴백으로 커밋합니다. 이 폴백도 기존 파일을 덮어쓰지 않지만, 확인과 이름 변경 사이의 짧은 틈은 원자적으로 보호되지 않습니다 — 같은 목적지에 동시에 쓰는 다른 프로세스가 있다면 이런 파일시스템에서는 그 보장이 최선 노력(best effort)으로 낮아집니다.

재실행 시 이미 처리된 파일을 건너뛰는 판정은 원본 파일의 크기·수정 시각과, 목적지를 결정하는 설정(목적지 경로, 분류 전략, 이벤트명, unclassified/quarantine 경로), 그리고 비디오의 XML sidecar(선택된 경로·크기·수정 시각·내용 해시)를 기준으로 합니다. 따라서 sidecar 내용이나 `M01.XML ↔ M01.xml` 경로가 바뀌면 파일을 다시 분류합니다.

목적지가 NAS 마운트일 때, 이 도구는 경로 문자열만 확인하고 볼륨/디바이스 identity는 검증하지 않습니다. NAS가 해제된 상태에서 마운트포인트가 로컬 디스크에 쓰기 가능하면, 백업이 로컬 디스크에 기록되고도 성공으로 보고될 수 있습니다. 실행 전 목적지 마운트가 실제로 연결되어 있는지 확인하세요.

일반 파일 I/O가 NAS 장애로 커널 호출 안에서 멈춘 경우에는 해당 호출이 반환될 때까지 취소 신호를 처리할 수 없습니다. 또한 SIGKILL이나 전원 장애처럼 정상 정리 절차를 거치지 못한 종료에서는 애플리케이션 전용 랜덤 이름의 `.part` 파일이 남을 수 있으며, 현재 시작 시 자동 삭제하지 않습니다. 정상 취소와 오류 경로에서는 `.part`를 정리합니다. 임시 파일의 최종 rename은 부분 파일 노출을 막지만 파일과 부모 디렉토리를 `fsync`하지 않으므로 전원 장애 직후의 영속성까지 보장하지는 않습니다.

### 6. 백업 검증

상단의 **검증** 탭에서 원본 폴더와 백업 도착 폴더를 새로 스캔해 실제 파일끼리 대조합니다. 기존 백업 기록에 의존하지 않으므로 "이 SD카드, 포맷해도 되나?"를 확인하는 용도로 사용할 수 있습니다.

- **빠른 모드**: 이름과 크기로 대조. 동명 사본이 여럿이면 오매칭 가능성을 경고로 안내
- **정밀 모드**: SHA-256 내용 해시로 대조 (이름·위치 무관)
- **해시 목록 대조** (정밀 모드 옵션): NAS처럼 도착 폴더 전체 읽기가 느린 환경에서는 NAS 쪽에서 생성한 해시 목록 파일을 업로드해 도착 폴더를 읽지 않고 대조

문제 파일(누락·불일치)은 결과 화면에서 확인 후 **다음 백업 때 다시 복사되도록 예약**할 수 있습니다. 해시 목록에 형식 오류가 있거나 도착 폴더 일부를 읽지 못한 경우에는 파일 부재를 확정할 수 없으므로 예약이 비활성화됩니다.

검증은 원본·도착의 어떤 파일도 수정하지 않습니다. 재복사 예약을 확정할 때만 상태 파일이 갱신됩니다.

### 7. CLI 모드

```bash
VERSION=$(git describe --tags --always --dirty)
go build -ldflags="-X main.version=${VERSION}" -o bin/shutterpipe ./cmd/shutterpipe
./bin/shutterpipe run -s /Volumes/SD_CARD -d /Volumes/NAS/Photos
```

주요 옵션
- `-c, --config`: 설정 파일 경로 (YAML/JSON)
- `-s, --source`: 원본 경로
- `-d, --dest`: 목적지 경로
- `-e, --include-ext`: 포함할 확장자 목록 (예: `-e jpg -e mp4`)
- `-j, --jobs`: 병렬 워커 수 (0=자동)
- `--dedup`: `name-size` 또는 `hash`
- `--conflict`: `skip`, `rename`, `overwrite`, `quarantine`
- `--unclassified-dir`: 분류 불가 폴더명
- `--quarantine-dir`: 격리 폴더명
- `--state-file`: 상태 파일 경로
- `--log-file`: 로그 파일 경로
- `--log-json`: JSON 로그 출력
- `--dry-run`: 복사 없이 시뮬레이션
- `--hash-verify`: 해시 검증 옵션

날짜 필터(`date_filter_start`, `date_filter_end`)는 현재 설정 파일(`--config`)에서 지정할 수 있습니다.
`hash_verify`를 활성화하면 복사 중 읽은 원본 바이트, 완성된 임시 파일, 복사 후 다시 읽은 안정된 원본의 SHA-256을 모두 비교한 뒤 검증에 성공한 파일만 최종 경로에 반영합니다. 복사 전후의 원본 파일 identity·크기·수정 시각도 비교하므로 복사 도중 바뀐 원본의 혼합 스냅샷은 게시하지 않습니다.

웹 UI와 CLI는 `~/.shutterpipe/run.lock`의 프로세스 간 잠금을 공유합니다. 한 백업이 실행 중이면 다른 웹 서버 프로세스나 CLI의 동시 백업은 실패하여 상태와 이력이 서로 덮어쓰이는 것을 방지합니다.

### 버전 확인

```bash
./bin/shutterpipe version
```

## 설정 옵션

### 기본 설정

| 옵션 | 설명 | 기본값 |
|------|------|--------|
| 분류 방식 | 날짜별 또는 이벤트별 | 날짜별 |
| 이벤트명 | 이벤트별 분류 시 폴더명에 추가 | (비어 있음) |
| 날짜 필터 | 특정 기간 파일만 백업 (시작일~종료일) | 전체 |
| 충돌 정책 | Skip/Rename/Overwrite/Quarantine | Skip |
| 중복 검사 방법 | 이름+크기 또는 해시 | 이름+크기 |
| Dry Run | 실제 복사 없이 시뮬레이션 | Off |
| 해시 검증 | 해시 검증 옵션 활성화 | Off |
| 이전 기록 무시 | 상태 파일 무시하고 전체 재수행 | Off |

### 고급 설정

| 옵션 | 설명 | 기본값 |
|------|------|--------|
| 병렬 워커 수 | 동시 처리 파일 개수 (0=자동, 최대 32) | 자동 (CPU 코어 수, 최대 32) |
| 포함할 확장자 | 특정 확장자만 필터링 | jpg, jpeg, heic, heif, png, raw, arw, cr2, nef, dng, mp4, mov, avi, mkv, mxf, xml |
| 분류 불가 폴더명 | 메타데이터 없는 파일 저장 폴더 | unclassified |
| 격리 폴더명 | 충돌 시 격리 정책 사용 폴더 | quarantine |
| 상태 파일 경로 | 처리 이력 저장 파일 | ~/.shutterpipe/state.json |
| 로그 파일 경로 | 로그 저장 경로 | ~/.shutterpipe/shutterpipe.log |
| JSON 형식 로그 | 로그를 JSON 형식으로 저장 | Off |

## 설정 파일

CLI에서 `--config`로 YAML/JSON 설정 파일을 불러올 수 있습니다.

```yaml
source: "/Volumes/SD_CARD"
dest: "/Volumes/NAS/Photos"
organize_strategy: "date" # date | event
event_name: "크리스마스"
date_filter_start: "2026-01-01" # 선택사항: 특정 기간만 백업
date_filter_end: "2026-01-31"
include_extensions: ["jpg", "mp4"]
jobs: 0
conflict_policy: "skip"
dedup_method: "name-size"
unclassified_dir: "unclassified"
quarantine_dir: "quarantine"
state_file: "/absolute/path/to/.shutterpipe/state.json"
log_file: "/absolute/path/to/.shutterpipe/shutterpipe.log"
log_json: false
dry_run: false
hash_verify: false
ignore_state: false
```

설정 파일의 경로 값은 `~`가 자동 확장되지 않으므로 절대 경로를 사용하세요.

## 프리셋

자주 사용하는 설정을 프리셋으로 저장할 수 있습니다.

- 앱 바 우측의 **프리셋 ▾** 버튼 클릭 (또는 실행 화면의 "프리셋 불러오기" 링크)
- 실행 화면의 "프리셋으로 저장" 버튼으로 현재 설정 저장
- 프리셋 카드의 불러오기(↓) 버튼으로 적용
- 프리셋 파일 위치: `~/.shutterpipe/presets/`

## 데이터 저장 위치

ShutterPipe는 설정, 프리셋, 북마크, 경로 히스토리, 백업 이력을 서버 측 JSON 파일로 저장합니다.

```
~/.shutterpipe/
├── settings.json       # 현재 설정 (분류 방식, 충돌 정책 등)
├── bookmarks.json      # 북마크한 경로 목록
├── path-history.json   # 경로 자동완성 히스토리
├── backup-history.json # 백업 실행 이력 (최근 100개)
├── presets/            # 저장된 프리셋 파일들
│   ├── 일상촬영.json
│   └── 행사촬영.json
├── state.json          # 처리 상태(재실행 시 중복 처리 방지)
├── run.lock            # 웹/CLI 동시 백업 방지용 프로세스 잠금
└── shutterpipe.log     # 파이프라인 로그
```

상태 파일은 임시 파일을 동기화한 뒤 원자적으로 교체합니다. 이전 형식의 상태 항목은 안전을 위해 최초 1회 다시 처리되며, 새 항목은 원본과 목적지의 크기·수정 시각을 확인합니다. `hash_verify`가 켜진 실행은 두 파일의 저장된 해시도 재검증합니다. 파일 복사는 끝났지만 상태나 이력 저장이 실패한 경우 실행 결과에는 성공 여부와 별도로 경고가 포함되고 웹 로그에 표시됩니다.

### 다중 브라우저 지원

설정 데이터가 서버에 저장되므로:
- 같은 서버에 접속하는 모든 브라우저가 동일한 설정을 공유합니다.
- 브라우저 캐시를 삭제해도 설정이 유지됩니다.
- `~/.shutterpipe` 디렉토리를 백업하면 모든 설정을 보존할 수 있습니다.
